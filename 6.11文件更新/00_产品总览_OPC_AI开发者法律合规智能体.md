# OPC AI 开发者法律合规智能体
# 产品总览文档

**版本：** v1.2
**日期：** 2026-06-11
**文档性质：** 产品全貌索引与架构说明

---

## 一、产品定位

**服务对象：** 在中国大陆开发和运营 AI 产品的技术团队、产品团队和法务/合规负责人

**解决的核心问题：** AI 产品的法律合规义务覆盖产品全生命周期——从立项、开发、上线到持续运营，每个阶段的合规问题不同、触发条件不同、应对方式也不同。开发者最常见的失误，是在错误的时间做合规（上线前才发现需要提前6个月准备的备案，或者上线后才发现隐私政策缺少必要条款），或者根本不知道自己触发了哪些义务。

**产品核心价值：** 将法律合规转化为可操作的工程问题——在正确的时间，告诉开发者正确的事情，并直接输出可用的文件和工具，而不是停留在抽象的法律建议层面。

## 二、产品架构：四环节线性推进

OPC 的核心逻辑是**一条贯穿产品生命周期的主线**，四个环节严格对应产品研发的四个阶段，必须按顺序推进，后一环节的输入依赖前一环节的输出。

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  产品阶段        立项 / 概念设计    →    开发    →    上线前    →    运营期
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  核心问题        这个方向能做吗？       怎么做才        上线前要         上线后怎么
                                       合规？          交什么材料？      保持合规？
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  对应环节           Part A              Part B           Part C           Part D
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  主要输出        风险简报             合规评审报告      上线合规          合规状态
                （内部版+展示版）      + 合规文档草稿    文档包（ZIP）      仪表盘
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### 环节间的数据流

```
Part A 输出
  ├─ 风险条目列表（含等级/触发原因/法规依据）
  ├─ 数据类型清单
  ├─ 行业场景标签
  └─ 跨境传输标志
        │
        ▼ 自动导入
Part B 接收 → 生成开发期合规动作清单 → 逐项完成 → 生成草稿文档
  ├─ 合规清单完成状态
  ├─ 隐私政策草稿
  ├─ 用户服务协议要点清单草稿
  ├─ PIPIA 草稿
  └─ 第三方信息共享清单草稿（含SDK及API）
        │
        ▼ 可选导入
Part C 接收 → 格式规范化 → 补全 → 版本化 → 打包交付
  ├─ 《国内上线合规文档包》（ZIP）
  │    ├─ 前台展示包（用户协议/隐私政策/AI特别说明等）
  │    ├─ 备案申报包（算法备案/生成式AI备案/深度合成备案等）
  │    └─ 内部留档包（内部制度/RoPA/AI内容治理制度等）
  └─ 产品配置档案（传递给 Part D）
        │
        ▼ 自动导入配置
Part D 接收 → 持续监测 → 周期提醒 → 变更核查 → 应急响应
  ├─ 法规动态监测与影响评估
  ├─ 周期性义务日历
  ├─ 变更触发合规核查
  └─ 安全事件应急响应工具包
```

## 三、各环节定位与边界

### Part A — 设计期风险识别

| 项目 | 内容 |
|------|------|
| **服务阶段** | 产品概念与初始方案设计阶段（立项前） |
| **核心问题** | 这个产品/功能方向能不能做？做了会触发哪些监管义务？ |
| **输入** | 产品描述（表单填写 或 PRD文档上传） |
| **输出** | 《AI产品立项前风险简报》内部决策版 + 对外展示版 |
| **风险维度** | ①政策合规风险 ②行业专项风险 ③数据合规风险 ④产品交互合规风险 |
| **风险等级** | 5级：🟢低风险 / 🟡中风险 / 🟠高风险 / 🔴谨慎推进 / ⛔禁止 |
| **与下一环节的关系** | Part A 的风险条目、数据类型清单、行业场景、跨境标志全部自动导入 Part B，成为 Part B 合规动作清单的生成依据。**Part A 做得越完整，Part B 的动作清单覆盖越准确。** |

**使用时机：** 产品方向刚确定、PRD 刚完成、向内部决策层或投资方汇报前。

---

### Part B — 开发期合规评审

| 项目 | 内容 |
|------|------|
| **服务阶段** | 立项确认后 → 测试上线前（贯穿整个开发周期） |
| **核心问题** | 开发过程中，每个技术决策和功能实现是否满足合规要求？ |
| **输入** | Part A 风险报告（自动导入）或独立填写配置表单 |
| **输出** | 《开发期合规评审报告》（进度跟踪版）+ 合规文档草稿（隐私政策/PIPIA/SDK清单等） |
| **合规清单维度** | ①数据架构合规 ②同意与告知机制 ③AI内容安全 ④第三方依赖合规 ⑤日志与审计 |
| **法域覆盖** | B-CN（中国合规主轨，所有用户默认）+ B-EU（欧盟 GDPR + EU AI Act，服务欧盟时解锁） |
| **与下一环节的关系** | Part B 的配置数据和草稿文档可直接导入 Part C，避免重复填写；Part B 完成的合规动作为 Part C 的文件生成提供内容基础。**Part B 做得越扎实，Part C 的文件质量越高、需要人工补充的内容越少。** |

**使用时机：** 开发启动时创建项目，开发全程持续更新，直到上线前标记全部高优先级项"已完成"。

---

### Part C — 国内上线合规模板中心

| 项目 | 内容 |
|------|------|
| **服务阶段** | 开发完成 → 正式对外提供服务前（上线冲刺阶段） |
| **核心问题** | 上线前需要准备哪些文本和材料？哪些需要向监管机构提交？ |
| **输入** | Part B 配置与草稿（可导入）或独立填写产品配置表单 |
| **输出** | 《国内上线合规文档包》（ZIP）= 前台展示包 + 备案申报包 + 内部留档包 |
| **文档分类** | C1 前台法律文本（6类）+ C2 监管/备案申报材料（4类）+ C3 内部治理与留档（5类） |
| **三档分级** | 必备文件（法规强制）/ 建议文件（合规基础设施）/ 可能触发备案（需核查门槛） |
| **与下一环节的关系** | Part C 完成后，将产品配置档案传递给 Part D，作为 Part D 监测规则匹配和义务日历生成的基础。**Part C 的文件包是 Part D 监控文件有效性的起点。** |

**使用时机：** 开发基本完成、进入测试阶段，预计上线前 4—8 周启动。备案类材料（生成式AI备案/算法备案）建议在此基础上提前 2—3 个月启动。

---

### Part D — 运营期持续合规监测

| 项目 | 内容 |
|------|------|
| **服务阶段** | 产品上线后 → 持续运营期间（无限期） |
| **核心问题** | 上线之后，我如何保持合规状态不失效？ |
| **输入** | Part C 产品配置档案（自动导入）；法规监测系统；用户提交的变更/事件信息 |
| **输出** | 合规状态仪表盘 + 法规影响分析报告 + 义务日历 + 变更核查记录 + 应急响应工具包 |
| **四个子模块** | D1 法规动态监测 / D2 周期性义务日历 / D3 变更触发核查 / D4 安全事件应急响应 |
| **与前序环节的关系** | D1 发现法规变化影响已有文件时，直接跳转 Part C 对应文档进行更新；D3 产品变更核查完成后，触发 Part C 文档版本迭代，形成版本历史。**Part D 是整个合规生命周期的闭环收口。** |

**使用时机：** 产品上线后立即启动，持续运行。

## 四、核心设计原则

### 原则一：顺序不可跳跃，输入不可断链

四个环节的顺序是**刚性约束**，不是建议：

- 没有 Part A 的风险识别，Part B 的动作清单覆盖不完整
- 没有 Part B 的开发期落地，Part C 的文件内容无法自动填充
- 没有 Part C 的文件基线，Part D 无法监控文件有效性

允许独立使用单个模块（例如团队从 Part B 独立启动，或直接进入 Part C），但系统会标注"未关联上游数据，覆盖可能不完整"的警示，并建议补做上游评估。

### 原则二：风险在最早的时间点识别，代价最低

```
立项前识别 → 调整产品方向              成本：低（仅设计改动）
开发中识别 → 修改代码架构              成本：中（工程返工）
上线前识别 → 紧急补文件 / 延迟上线      成本：高（影响节奏）
上线后识别 → 被罚款 / 被下架 / 补备案   成本：极高（业务中断风险）
```

OPC 的分层设计目标：**将 80% 的合规问题消灭在 Part A/B 阶段**，让 Part C 只做最后的格式化收尾，而不是第一次发现问题的地方。

### 原则三：每条合规义务可溯源、可证明

每条 Part A 风险条目，在 Part B 中必须有对应的处理记录，不允许断档。Part B 完成的动作生成对应文件，文件反向关联风险条目。整条链路形成"风险 → 动作 → 文件"的可追溯闭环，支持：
- 内部审计核查
- 投资方尽职调查
- 监管检查应对

### 原则四：输出直接可用，不止于建议

每个环节的输出都是**可直接使用的材料**，而非需要进一步加工的建议：

| 环节 | 输出形态 |
|------|---------|
| Part A | PDF 报告（内部决策版 / 对外展示版），可直接向投资方/甲方呈现 |
| Part B | 合规清单（可分配负责人/截止日期，可导出进度报告）+ 文档草稿 |
| Part C | 可直接提交给监管机构的备案材料 + 可直接部署到产品前台的法律文本 |
| Part D | 可直接使用的事件通知模板 + 审计报告框架 + 义务日历（可导出 .ics） |

### 原则五：辅助生成，不替代专业判断

OPC 是合规辅助工具，不是法律服务机构，不构成律师意见或法律顾问意见。

平台生成的所有文件——包括风险报告、隐私政策、备案申报材料、内部制度——均基于用户填写的配置信息和系统内置的法规逻辑自动生成。文件质量直接取决于用户输入信息的准确性和完整性；法规解释的正确性取决于系统更新的及时性。

**以下场景强烈建议在正式使用前寻求专业法律顾问审核：**
- 向监管机构正式提交的备案申报材料（生成式AI备案/算法备案/深度合成备案）
- 面向大规模用户公示的隐私政策和用户协议
- 个人信息保护影响评估报告（PIPIA）
- 涉及金融/医疗/政务行业场景的合规文件
- 数据安全事件的对外通知和监管报告

平台在每份文件生成时均附有版本号和生成日期标注，供团队内部版本管理使用，不在文件正文中添加任何提示性文字，导出后可直接作为正式文件使用。

## 六、典型使用路径

### 路径一：全流程使用（推荐）

```
1. 产品立项时        → Part A：填写产品描述，生成风险简报，确认产品方向
2. 开发启动时        → Part B：从 Part A 导入，创建合规项目，分配责任人
3. 开发过程中        → Part B：持续更新合规清单状态，完成各维度动作
4. 开发完成/测试阶段  → Part C：从 Part B 导入，生成并下载上线合规文档包
5. 上线后即刻        → Part D：导入配置，启动法规监测和义务日历
```

### 路径二：从 Part C 独立进入（已开发完成的产品）

```
现有产品需要补做合规 → Part C：独立填写配置表单 → 生成文档包
                   → Part D：导入配置，开始运营期监测
                   → 建议回溯做 Part A/B 评估，补全合规记录
```

### 路径三：从 Part B 独立进入（开发中途接入）

```
开发进行中 → Part B：独立填写配置（系统提示"建议补做 Part A"）
          → 完成开发期合规动作和文档 → 进入 Part C → Part D
```
